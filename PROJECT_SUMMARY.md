# Tralyn — Project Summary

A technical case study of Tralyn, an independent full-stack warehouse inventory management project. For setup and reference documentation, see the [README](README.md).

## 1. Context

Tralyn is a portfolio engineering project inspired by a real warehouse workflow I observed in the sustainable-energy sector, where stock was tracked in a spreadsheet. I built it independently, to explore how far data integrity can be pushed into the database. All data in this repository is fictional.

## 2. Problem

A spreadsheet stores the *current* stock as a number in a cell. That number can be overwritten, and once it is, the reason for the change is gone. There is no reliable link between a balance and the events that produced it, no real separation between people who read stock and people who change it, and no safe way to move years of data into a new system without losing or duplicating something.

I framed the project around one question: what would it take for every unit of stock to be explainable?

## 3. Engineering Decisions

- **No stock column.** Stock is derived from an append-only movement ledger, never stored as an editable value.
- **The database is the authority.** Permissions and integrity rules live in PostgreSQL (Row Level Security, an RPC, constraints and triggers). The UI only mirrors them for usability.
- **Least privilege at runtime.** The web application talks to the database as the signed-in user, with the public key; it holds no privileged credentials.
- **Fail-closed migration.** Legacy data enters through a pipeline that refuses anything unexpected, instead of "fixing" it silently.
- **Reproducibility.** A fictional canonical workbook and a one-command local demo make every claim checkable from a fresh clone.

## 4. Architecture

Next.js 16 (App Router, Server Components and Server Actions) renders the interface and validates input with Zod. Supabase provides authentication and PostgreSQL. A proxy requires a session on every route, a data access layer refuses inactive profiles, and every query runs under Row Level Security. Stock movements are written through a single `SECURITY DEFINER` RPC. Command-line tooling for imports and administration lives outside the web application. The intended deployment is Vercel with a hosted Supabase project.

## 5. Stock Ledger

The `stock_movements` table holds five movement types: `OPENING_BALANCE`, `IN`, `OUT`, `ADJUSTMENT_IN` and `ADJUSTMENT_OUT`. Quantities are always positive, and the type defines the direction. A view, `product_stock`, sums the ledger into the current balance and derives the status (OK, reorder, out of stock) from each product's minimum stock.

Triggers reject `UPDATE`, `DELETE` and `TRUNCATE` for every role. A `BEFORE INSERT` trigger locks the product row and refuses any output above the balance, so concurrent exits on the same product are serialized and stock can never go negative. The responsible user comes from the session and the timestamp from the database clock; neither is a parameter. Mistakes are corrected with visible adjustments, never by editing history.

## 6. Database Authorization

There are three roles. Administrators can do everything, operators can register entries and exits, and viewers can only read. The movement RPC checks the role per movement type, and rejects `OPENING_BALANCE` for every role: opening balances exist only on the technical import path. Row Level Security limits reads to active profiles and writes on master data to administrators. A trigger prevents removing or demoting the last active administrator.

Because the UI and the database both encode the permission matrix, a test compares them for every role and movement type, so they cannot silently drift apart.

## 7. Legacy Migration

Importing into an immutable ledger cannot be undone, so the pipeline is built around proving correctness *before* writing:

1. **Parse** the workbook, requiring exact sheets, headers and cell types.
2. **Normalize** text (trimming, Unicode NFC) without type coercion.
3. **Validate** against expectations, including the file's SHA-256 and the workbook's own computed totals.
4. **Plan** deterministically: the same file always yields the same plan and the same source references.
5. **Dry-run** inside a transaction that is always rolled back.
6. **Apply** in one transaction, with an advisory lock, a baseline check and exact invariants verified before the commit.
7. **Audit** every run in append-only batch and record tables, attributed to a technical identity that cannot sign in.

Re-running an import records items as *already present* instead of duplicating them. For the public repository, I replaced the private data with a fictional workbook that reproduces the original format and its edge cases, generated byte-for-byte reproducibly from code.

## 8. Testing Strategy

The test suites mirror the layers of responsibility:

- **Unit (447):** validation, permissions, ledger rules, the import pipeline and the canonical workbook.
- **Database / integration (237):** run against a local Supabase stack, with real signed-in users per role, so RLS, the RPC, the triggers and concurrency are exercised for real.
- **End-to-end (61):** Playwright against a production build, including mobile navigation and responsive layouts.
- **Demo environment (3):** the demo is repeatable, its roles are enforced by the database, and it refuses non-local targets.

Type checking, linting, the production build and database linting complete the gate.

## 9. Demo Architecture

`npm run demo:setup` rebuilds a complete demo on the local stack: it resets the database, provisions the technical identity and three fictional users, imports the canonical workbook through the real pipeline, creates suppliers and projects through the application's services, and registers operational movements through the RPC as those users. It then verifies the final state against pinned invariants.

The canonical import state and the visual demo state are kept separate on purpose: the extra movements make the demo more representative without weakening the migration tests. A pure guard refuses to run unless every signal points at the local stack, and the command has no bypass option.

## 10. Challenges and Trade-offs

- **Derived stock versus speed.** Summing a ledger is slower than reading a column. A view is fast enough at this scale; much larger catalogs would call for pagination or a maintained snapshot that is still derived from the ledger.
- **The database clock owns time.** Operational movements cannot be backdated; only the audited import preserves historical dates.
- **Strictness versus convenience.** A fail-closed importer rejects files that a lenient one would accept. I chose to stop and explain, rather than guess.
- **Defense in depth costs duplication.** Mirroring permissions in the UI and the database means two places to maintain, which is why a parity test exists.
- **One local stack, two uses.** The demo and the integration tests share the local database, so the database tests refuse to run on top of the demo, with a clear instruction.

## 11. What I Learned

- Designing the data model around the question "how did we get here?" simplified everything else.
- Putting the rules in PostgreSQL makes them testable on their own, and impossible for any client to bypass.
- Irreversible operations deserve a rehearsal: a dry-run with the same code path is worth more than any amount of review.
- Reproducible fixtures turn claims in a README into something a reviewer can verify.
